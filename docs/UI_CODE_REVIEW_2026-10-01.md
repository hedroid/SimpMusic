### UI-CR-02 视频 tab 操作会误删音频且无法重下视频【P1·已修：主仓 d92a4bda】

原实现的 `viewMode` 只影响行展示，暂停、重试、重下、删除仍调用整首级 API。VIDEO tab 点“重下”会先删除
音频和视频，再只调用 `downloadTrack()`；点“删除”也会连音频一起删除，批量删除同样受影响。

修复复核：

- `LibraryDynamicPlaylistViewModel` 新增 `redownloadVideo()` 与 `deleteVideoOnly()`。
- 行内重下、单行删除确认、多选批量删除均按 `isVideoTab` 分流。
- 暂停/恢复/重试维持任务级双条目语义，对已完成音频条目无副作用。

验证边界：提交记录说明已通过代码走查与编译，但模拟器受 YT 风控影响没有视频样本，仍需真机验证“音频已完成、
视频缺失/失败”时的重下和单删。

### UI-CR-03 磁盘拒绝入队后永久停在准备下载【P1·已修：主仓 d92a4bda】

原流程在调用 `downloadTrack()`/`downloadVideo()` 前先将 Room 写成 `STATE_PREPARING`，却忽略入队函数返回的
Boolean。剩余空间低于 500 MB 时函数返回 `false` 且不会创建任务，因此没有 DownloadManager 状态能纠正 UI，
歌曲或容器会永久显示“准备下载”。

修复复核：三点菜单覆盖/新下载、多选、歌单、专辑入口已统一检查返回值；任一任务被磁盘预检拒绝时回滚
`STATE_PREPARING -> STATE_NOT_DOWNLOADED`，并提示“存储空间不足，无法下载”。

验证边界：尚未通过真实低磁盘环境验证；需要覆盖音频、视频以及批量中部分成功/部分拒绝三种情况。

### UI-CR-04 清除全部下载遗漏 state 1/2 活动行【P1·已修：core 21d0813】

原 `removeAllDownloads()` 使用 `getDownloadedSongs()`，只查询 `downloadState=3`。当音频已落地、视频仍在下载或
暂停时，歌曲处于 state 1/2 且仍持有音频路径；清除操作不会删除文件和清 Room，却会继续移除 DownloadIndex，
留下文件和卡死行。

修复复核：数据源已改为 `getDownloadActivitySongs()`，覆盖 `state in 1/2/3 OR 音频/视频路径非空`；仍保持
“先删文件、清路径、落 state 0、清 landed 标记，再移除 DownloadIndex”的顺序。

### UI-CR-05 网易 MP3 被二次有损转码【P2·已修：core 21d0813】

原调用只位于 `ext != flac` 分支，却传入 `copyAudio = isNetease && isFlac`，条件恒为 false，导致网易
128/192/320 kbps MP3 全部再次经过 `libmp3lame -q:a 0`。

修复复核：网易 MP3 现使用 `-c copy` 容器级重封，YT webm 输入才走 MP3 编码。提交记录中的模拟器实测结果：
128 kbps 源落盘仍为 128 kbps，标题、歌词、MJPEG 封面存在，ExoPlayer 可正常播放。

### UI-CR-06 系统栏对比度跟随全局主题而不是页面背景【P1·已修：主仓 62afc040】

证据：

- `Theme.kt` 为沉浸式页面计算 `forcedDarkScheme`，但仍以全局 `isDark` 调用 `SystemBarAppearanceEffect`。
- `PlatformColorScheme.android.kt` 直接以 `!isDark` 设置状态栏与导航栏图标明暗。
- 当前模拟器深色封面页面可见黑色状态栏图标落在深紫/黑色背景上。

修复复核：

- `AppTheme` 持有 `LocalForceDarkSystemBarDepth`（`MutableIntState`），`ForceDarkContent` 以
  `DisposableEffect` 进出组合时增减；系统栏效果改读「全局深色 OR 沉浸计数 > 0」，读取隔离在
  独立小 composable 里，计数变化只重组该节点。
- `ForceDarkContent` 新增 `affectSystemBars` 参数：平板横屏/桌面 35% 侧栏传 false——状态栏左半边
  压在随全局主题的页面上，翻图标只是把不可读的一半从面板挪到时钟。
- 模拟器实证（浅色主题）：库页状态栏深色图标（3315 暗字像素）→ 歌单详情白色图标（3305 亮字像素，
  时钟区 1789/电池区 1516）→ 返回库页翻回深色（3315），完整往返。

建议验收：浅色主题进入所有强制深色页面，状态栏时间、电量、网络图标保持清晰；滚动封面和渐变变化时不闪色。

### UI-CR-08 底部浮层系统侵占过多视觉空间【P1·待设计】

当前纵向手机布局由迷你播放器、四项导航胶囊和独立搜索圆钮组成。模拟器 1080×2424 样本中底部区域从
y=2003 延续到 y=2424，约占屏幕高度 17%。代码已有安全区让位，因此不是简单的点击遮挡 bug；问题是透明玻璃
仍让页尾、列表内容和播放器在视觉上粘连，内容区域显得被底部“大块 UI”持续压缩。

建议方向：

- 迷你播放器收敛到 64–72dp，减少次要操作或移入展开页。
- 搜索若继续作为一级目的地，直接并入导航；否则移到顶栏。
- 底部系统使用统一轮廓和材质，并在内容交界处增加稳定的 tonal scrim/渐变，不完全依赖背景采样。
- 保留现有内容层底部预留，禁止重新引入迷你条关闭时的页面跳动。

### UI-CR-09 搜索与音源切换的交互语义冲突【P2·待设计】

`LiquidGlassAppBottomNavigationBar` 明确把 Search 从 tab 列表拆出为独立 FAB，同时把核心音源切换藏在长按搜索按钮中。
这造成两个冲突：搜索是导航目的地却看起来像即时动作；音源切换是全局模式却没有可见入口。

建议：音源入口放到头像、主页/搜索顶栏或带品牌标识的显式菜单；长按只作为快捷方式，不能作为唯一发现路径。

### UI-CR-10 库页混合多个导航维度【P2·待设计】

建议选择唯一一级轴：

- 推荐：chip 只切“网易 / YouTube / 本地”，内部用稳定分区组织歌单、专辑、艺人、播客和下载。
- 若保留“网易播客”独立 chip，则移除同页播客磁贴，并明确它是独立产品区而非库筛选。

### UI-CR-11 视觉语言缺少统一约束【P2·待设计】

`LibraryTilingBox.kt` 为七类入口定义七套固定高饱和颜色；同屏还存在主题 seed 色、网易/YT 品牌色、真实封面色、
描边 chip 与液态玻璃。建议建立明确配额：

- 品牌色只表达来源。
- primary 只表达选择和主操作。

- 统一圆角、容器层级和阴影，不让 ElevatedCard、玻璃与纯色块同时竞争。

### UI-CR-14 库页标题动画依赖时序补丁【P2·待重构】

库页通过 `showTitleBar` 改变顶部几何高度，随后用 500ms 静默窗、`pendingTitleFlip` 延迟回放及下载管理页特例，
阻止布局变化继续触发滚动上报。这解决了已有振荡，但结构本身仍脆弱，且静默窗可能吞掉快速反向手势。

建议：

- 标题区域保留固定测量高度，仅用 `translationY/alpha` 改变呈现。
- 用方向、阈值和滞回决定收展，而不是依赖墙钟静默期。
- 下载管理、空态、网格和长列表共用同一嵌套滚动契约。
- 验收必须包含快速来回拖动、列表底部、内容不足一屏、切 chip 恢复深滚动位置。

### UI-CR-15 chip 选中项不保证可见【P3·已修：主仓 052e01fc】

库页 chip 使用 `rememberScrollState + Row.horizontalScroll`，切源、恢复状态或程序设置 `currentFilter` 时没有把选中项
滚入可视区域。建议改为有 key 的 `LazyRow`，状态变化后按 index 执行 `animateScrollToItem`，并用边缘渐隐提示仍有
更多项目。

修复复核：

- `Row.horizontalScroll` → `LazyRow + rememberLazyListState`（同样 saveable，切页返回保留滚动位），
  可见 chip 列表折成 `visibleLibraryChips`（显隐规则与渲染同源），按 enum key 渲染。
- 新增 `LaunchedEffect(currentFilter, 两可见性)`：选中项不完全在视口内才 `animateScrollToItem` 滚入
  （回落弹回/切源/登出重定向/深滚动位恢复后有当前位置反馈；完全可见时不动，避免与用户手点打架）。
  可见性作 key：chip 集合增删时同一选中项的 index 平移也覆盖。
- 验证边界：现行门控下可见 chip 恒 ≤3（网易两+下载 或 YT 两+下载），常规屏不溢出——溢出场景
  （超大字体）机制已就绪但未可视化实测；基础行为（渲染/选中态/点击切页）模拟器实测通过。
  边缘渐隐未做（无溢出场景可观察，待有 4+ chip 时再补）。
